I have a clear picture of the bug. Here's the analysis:

Root Cause
The resolveRoute function tracks topPath per client — the path of the top-level page request (no referer) used to reconstruct filesystem paths for all subsequent file requests (JS/CSS imports).

The problem: Chrome on macOS automatically sends a GET /.well-known/appspecific/com.chrome.devtools.json request (DevTools protocol discovery). This request has:

No referer header (browser-initiated)
open: 0 (it's a file, not a directory)
The current condition on line 98 is:


if (!request.headers.referer || !props.topPath)
Because !request.headers.referer is true, it overwrites topPath with /.well-known/appspecific right after the page load set it correctly. All subsequent JS imports then resolve relative to that garbage path.

On Windows, Chrome doesn't make this request (or the timing differs), so topPath stays correct.

The Fix
The condition should only update topPath when:

topPath is not yet set (initial state), OR
There's no referer AND the request is an open (directory/page) request — a real navigation
This rejects the DevTools probe (open: 0, no referer) from overwriting an already-valid topPath.

const resolveRoute = (request, urlParts, props) => {
  let route = urlParts.path.split('/').slice(1);
  const isTop = !props.topPath || (!request.headers.referer && urlParts.open);
  if (isTop) { props.topPath = urlParts.path; props.topOpen = urlParts.open; }
  if (urlParts.path !== props.topPath) {
    const topRoute = props.topPath.split('/').slice(1); let offset = 0;
    while (route[offset] === topRoute[offset]) { offset++; }
    route = [...topRoute.slice(0, offset + props.topOpen), ...route.slice(offset)];
  }
  // log.debug(
  //   `resolveRoute referer "${request.headers.referer}", route [${route}] (${isTop}, ${urlParts.path !== props.topPath}): `,
  //   urlParts, props,
  // );
  return route;
};
